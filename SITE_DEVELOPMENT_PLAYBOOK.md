# Памятка по разработке сайтов: удачные решения и паттерны

Это каталог решений, применённых и проверенных на сайте DOSTUP. Это не шаблон для
слепого копирования: для каждого нового сайта нужно оценивать данные, риски, стоимость
и требования к доступу.

## Базовая архитектура

| Задача | Рекомендуемое решение |
| --- | --- |
| Небольшой внутренний сайт | Статический HTML, CSS и ES-модули; публикация на GitHub Pages. |
| Установка как приложение | PWA: `manifest`, иконки, service worker и продуманное обновление кэша. |
| Совместная работа с данными | Firestore с подписками `onSnapshot`, чтобы открытая вкладка видела изменения без ручной перезагрузки. |
| Внешние сайты/парсинг | Cloudflare Worker: он обращается к источнику, нормализует результат и не раскрывает секреты клиенту. |
| Регулярные проверки | Cloudflare Cron по UTC с расписанием, записанным в конфигурации Worker. |

## Безопасный алгоритм внешнего обновления

1. Worker читает только активные карточки с нужной ссылкой.
2. Сравнивает найденные сведения с текущими данными.
3. Записывает отдельный пакет *предложений* (`pending`): идентификатор запуска, время,
   проверенные записи, список «было → стало» и ошибки.
4. Клиент получает пакет через подписку БД и показывает модальное окно с отдельными
   флажками, выбором всех пунктов, «Применить выбранные» и «Отложить».
5. При применении использовать транзакцию/батч и удалять из pending-пакета только
   реально применённые пункты. Если из двух предложений принято одно, второе остаётся.
6. При отсрочке не удалять серверные данные: скрывать окно лишь в конкретном браузере,
   а в интерфейсе оставлять заметный индикатор.

## Уведомления

- Красный колокольчик в шапке показывает число неприменённых изменений и открывает
  список повторно.
- Анимация должна быть сдержанной и повторяться с разумным интервалом (в DOSTUP — раз
  в 10 секунд).
- Звук допустим как дополнительный сигнал один раз при поступлении нового пакета.
  Браузеры разрешают его только после первого действия пользователя; визуальная часть
  должна работать всегда.
- Подписка БД позволяет показать новое уведомление в уже открытой вкладке/PWA без
  перезагрузки.

## UX-паттерны карточек и реестров

- Не закрывать карточку кликом по фону; явные действия: сохранить, отменить, удалить.
- При удалении — отдельное подтверждение.
- Для дат открывать календарь кликом по полю; для времени использовать ограниченный
  набор понятных шагов, например 5 минут.
- Списки ближайших событий сортировать по ближайшей дате; завершённые дела показывать
  отдельно или внизу.
- Делать краткие информационные полосы кликабельными, но не смешивать переход к полосе
  и открытие полной карточки без необходимости.
- Для значимых изменений давать сравнение прежнего и нового значения.

## PWA и публикация

- При каждом изменении JS/CSS менять версию в ссылках и имя `CACHE_NAME` service worker.
- После публикации предупреждать пользователей установленного PWA, что может
  потребоваться полностью закрыть и вновь открыть приложение.
- Проверять изменения на обычном экране и мобильной ширине.

## Что нельзя переносить без доработки

- Не переносить клиентские коды доступа из простого внутреннего сайта в защищённую
  систему делопроизводства: они видны в клиентском коде.
- Не публиковать реальные Firestore-конфигурации, API-ключи, персональные данные и
  тестовые карточки.
- Не давать автоматике право незаметно менять юридически значимые или рабочие данные.

- [ ] В коммит попали только файлы текущего проекта.
