# Постоянные правила работы с сайтами

Этот файл задаёт общий порядок для всех будущих проектов сайтов в этой рабочей папке.
Он дополняется проектными инструкциями в подпапках; при противоречии приоритет имеют
задача пользователя и инструкции конкретного проекта.

## Начало работы

1. Сначала изучить структуру проекта, `README`, проектные `AGENTS.md`, состояние Git и
   существующие локальные изменения.
2. Не смешивать изменения разных сайтов и не добавлять в коммиты посторонние файлы.
3. Перед реализацией кратко зафиксировать цель, границы изменения и способ проверки.
4. Для затрагивающих данные функций сначала определить: что меняется автоматически,
   что требует подтверждения пользователя и как отменить ошибочное действие.

## Разработка и качество

- Сохранять данные только явными действиями пользователя; клик вне модального окна не
  должен закрывать карточку с несохранёнными изменениями.
- Для удаления всегда показывать понятное подтверждение.
- Использовать доступный интерфейс: явные подписи, заметные состояния, клавиатурная
  навигация, удобные элементы даты/времени и корректная мобильная вёрстка.
- Сначала выполнять локальную проверку синтаксиса и `git diff --check`, затем проверять
  ключевой пользовательский сценарий в браузере.
- При изменении PWA обновлять версии кэшируемых ресурсов и имя кэша service worker,
  чтобы установленное приложение не оставалось на старом коде.

## Данные, интеграции и безопасность

- Не помещать пароли, ключи API, токены, персональные сведения или рабочие документы в
  чат, коммиты, публичный GitHub или демонстрационные файлы.
- Секреты внешних сервисов хранить в механизме секретов соответствующей платформы, а не
  в клиентском JavaScript.
- Внешние сайты и парсинг подключать через серверный/Worker-слой; не обходить их прямо
  из браузера, если это создаёт CORS-, безопасность- или надёжностные проблемы.
- Автоматические проверки должны создавать предложения изменений, а не незаметно
  переписывать рабочие карточки. Пользователь должен видеть «было → стало» и выбирать,
  какие пункты применить.
- Простые коды в клиенте допустимы только как лёгкий барьер интерфейса. Для защищённых
  систем обязательны серверная аутентификация, ролевой доступ, правила БД и аудит.

## Публикация

1. Коммитировать только относящиеся к задаче файлы с понятным сообщением.
2. Перед push показать пользователю, что именно будет опубликовано, если публикация не
   была прямо запрошена.
3. После публикации сообщать URL, commit hash, результат проверки и известные задержки
   развертывания/распространения настроек.

## Переиспользование решений

Технические паттерны и рекомендации собраны в
[`SITE_DEVELOPMENT_PLAYBOOK.md`](SITE_DEVELOPMENT_PLAYBOOK.md). Перед созданием нового
сайта изучать его и выбирать только решения, подходящие назначению и уровню защиты
проекта.
